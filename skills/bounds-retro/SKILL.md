# Bounds retro

Use the work the user identifies; default to the current task's accessible conversation, diff, and check results. State the boundary and missing evidence. Do not search unrelated private histories or infer inaccessible sessions.

Find repeated corrections, avoidable retries, misleading checks, navigation delays, and unnecessary human decisions. Separate observed patterns from single incidents and plausible suggestions. A small task may have nothing worth changing.

For each worthwhile candidate, connect evidence to a cause and the cheapest durable improvement. Prefer, in order appropriate to the problem:

1. Structure that removes the mistake: one owner, clear interfaces, fewer competing paths.
2. An existing check repaired or wired correctly, then a focused new check if needed.
3. Better tooling or a navigation pointer where information was hard to find.
4. A short instruction for a judgment call that structure and checks cannot capture.

Inspect existing enforcement before proposing another rule. Additional standing prose has a maintenance cost; retire redundant guidance when an implemented mechanism replaces it. Do not turn every correction into global policy.

Return a short ranked set of evidence → proposed change → expected benefit → way to validate it. Avoid invented time savings or counts of human attention. If no supported pattern warrants action, say so.

A retrospective normally proposes changes. Implement only when already authorized, within the identified project. Prove a new check catches a representative mistake and still accepts valid work. Do not edit global instructions, install skills, publish histories, or create tracker tasks merely because they might improve future sessions.
