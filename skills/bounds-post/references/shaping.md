# Shaping a post

## Mine the material

Treat the sources as a quarry, not a script. Pull candidate fragments before outlining: a sharp sentence, a claim with its one-line reason, a short scene of what happened, a code snippet, an error message, a quote, a complaint or confession. Look for a leading word: one short coinage or plain metaphor that names the whole idea. If one fits, the title, transitions, and ending can hang on it. Most material has leftovers; the post ends when its argument is complete, not when the pile is empty.

## Ground before you lean

List what the reader brings: the concepts they already know. Every other concept must be introduced, with its name, before a later paragraph relies on it. The unit is the idea, not the word; a paragraph can depend on an unfamiliar idea with no jargon in sight. When the next paragraph needs something not yet introduced, either introduce it first or treat it as something the reader brings. Demanding too much up front shuts readers out; defining too much inside buries the opening.

## Choose the opening

Each candidate opening implies a different claim. The chosen one sets what the rest must do. If the draft drifts from what the opening promised, re-thread the draft or change the opening.

## Test each paragraph

- What does this paragraph give the reader that the previous one did not?
- If it is cut, what breaks?
- Is one sentence doing two jobs? Split it or pick one.
- Is this argument (prose) or parallel items (a list)?

## Pick the form on purpose

- Prose carries an argument; a list carries truly parallel items.
- Use a table only when the same fields repeat three or more times.
- Quote when the exact wording is the point; otherwise paraphrase.
- Use a code block for multi-line or runnable code, inline code for one identifier.
- Use a callout only for an aside that would derail the main line.

## Sentences

- Be specific. Not "schema changes can cause issues" but "a column rename fails the build".
- Mix sentence lengths. Split a sentence that carries two thoughts.
- Use the short everyday word and the real public name of a command, flag, or API.
- Define a named pattern the first time it appears, and call each thing by one name throughout.
- Have a view; a post is explanation, where opinion belongs. Keep step-by-step instructions in their own short section.
- Use periods or commas instead of em dashes. Keep "only" and "not" next to the word they change.
- Make every "it", "this", and "they" point at one obvious thing.
- End on a specific next step, open question, or result, never a generic conclusion.
